# ADR 0005: Project enablement with one environment description

- Status: proposed
- Date: 2026-11-16

## Context

ARchetipo is meant to work on very different projects: Next.js with Postgres, PHP with MySQL, and others. A business person should open any of them and see the running app without configuring anything (ADR 0004).

Today a project's environment is described by `.archetipo/environment.json` (ports, resources, preparation, inputs, checks) and `.archetipo/preview.json` (how the app starts), packaged at publication into `.archetipo/environment-recipe.json` with helper scripts (ADR 0003). Services are started by those scripts. `coaching-planner`, for example, starts Postgres with `docker run` from `scripts/archetipo/ambiente.sh`.

In the isolated runtime there is no container engine inside the environment, deliberately, so that recipe cannot prepare. Adding service binaries to the base image would cover only the services chosen in advance, force recipes into one branch per mode, and grow the image with every service.

When the description is missing or broken, the preview today always asks the AI to write or repair it, whoever the person is.

## Decision

### Enablement and use are two moments

- **Enablement** is done once per project by a technical person, by hand or with the AI in the technical conversation. Its result is the environment description, reviewed and merged like code.
- **Use** is what everyone else does. The CLI runs the description as written; the AI works on the product, never on the environment.
- In use, a missing description or a failed preparation reports that the project is not ready for this environment and who maintains it. The agent may propose a fix only as a change the maintainers review. It does not rewrite the description silently.
- Whether a session is enablement or use is a workspace setting the maintainers control. It is not inferred from the person.

### One description

`.archetipo/environment.yaml`, version 2, replaces `environment.json` and `preview.json`:

```yaml
version: 2
toolchain:
  image: ghcr.io/org/coaching-planner-toolchain:3   # optional; ARchetipo's base image otherwise
services:
  db:
    image: postgres:17-alpine
    port: 5432
    env: { POSTGRES_USER: user, POSTGRES_PASSWORD: password, POSTGRES_DB: coaching_planner }
    ready: [pg_isready, -U, user]
    expose:
      DATABASE_URL: postgresql://user:password@{host}:{port}/coaching_planner
prepare:
  - name: dependencies
    run: [npm, ci]
  - name: database
    run: [sh, scripts/archetipo/ambiente.sh, database]
inputs: [package.json, package-lock.json, prisma/**]
checks:
  unit: { run: [npm, test] }
preview:
  run: [sh, scripts/archetipo/ambiente.sh, anteprima, "{port}"]
  url: http://127.0.0.1:{port}/
  simulated: [google-login, google-calendar, jev]
```

- A simple step is written inline. Elaborate logic stays in scripts the file calls; scripts remain optional.
- YAML, like `config.yaml`, so maintainers can comment it.
- The published bundle remains an internal artifact generated by `publish`. Nobody edits it by hand.

### Services are declared, not started by the project

- The description says which services the project needs: image, port, environment, readiness command and the variables to expose.
- The CLI validates the declaration, starts **one container per service per checkout** with its own data volume, waits for readiness, and passes the exposed variables to every preparation step, check and preview with the real host and port.
- Services are removed with their data when the checkout is removed, through the existing cleanup contract.
- With `archetipo view` they run on the person's engine. With `archetipo view --isolated` the launcher starts them inside the environment, on its internal network only, under the same egress rules as the workspace and with no published port. The description and the recipe are the same in both modes.
- The project never runs the engine itself, which is never available inside the isolated environment.

### Toolchain

- The language runtime of the app (Node, PHP with its extensions, Python, Java…) comes from the toolchain image, built on ARchetipo's base image, which carries the CLI and the agents.
- The toolchain image is used **only for the workspace container**. The gateway always runs ARchetipo's own image, so nothing in a repository can change the boundary.

### Who decides what

| Level | Decides | Examples |
| --- | --- | --- |
| ARchetipo | The boundary | Gateway, egress rules; no privileges, host mounts, host network, engine socket or published service ports |
| Organization | What is allowed | Registries and images allowed for toolchains and services, resource limits, later the domain allowlist |
| Repository | What the project needs | Toolchain, services, preparation, checks, preview, accounts required |

The repository can request only what the organization allows. Images are pinned by digest when published.

### Enablement is verified, not assumed

- `archetipo execution environment verify` runs the whole description in the target mode: toolchain image, services, two preparations (the existing qualification), preview reachable, checks. Its report is retained like other evidence and names the ARchetipo version.
- The same command runs in CI on every change to the description, its inputs or its scripts, so a broken recipe is seen in the change that broke it.
- ARchetipo ships **starter descriptions** for common stacks (Next.js + Postgres, Laravel + MySQL, Django + Postgres + Redis…). A maintainer adapts one instead of starting blank.

### Compatibility

- The CLI keeps reading `environment.json` and `preview.json` during a transition. A conversion command writes `environment.yaml` from them.
- The public `execution environment …` and `execution preview …` operations keep their behaviour. New behaviour is additive.
- A recipe that starts services itself keeps working in local mode. In isolated mode it is reported as needing enablement, with the reason.

## Consequences

- Recipes stop depending on how services are started, and the same description serves both modes and a later remote runtime.
- The verification, recipe and preview packages read the new format. Changes there run `npm run test:harness-benchmark` as well as the Go checks.
- The launcher gains service containers, and the isolated policy gains rules for them.
- `archetipo-environment` writes one file, declares services instead of scripting them, and distinguishes enablement from use.
- A business person adding a project by URL either gets a ready project or a clear "not ready" with who to ask.
- ADR 0004's statement that services run as processes in the container is superseded by declared services.

## Open points

1. How the enablement/use setting is stored and who may change it.
2. Where the organization policy lives for a person without central administration: a default policy shipped with ARchetipo, overridable by a file the organization distributes.
3. Seed data across checkouts: every checkout starts from the project's seed; copying data between checkouts is out of scope.
4. Services that need files from the repository (an init SQL, a config): mounted read-only from the checkout or baked into a project service image.
5. Building toolchain images: by the project's CI and pulled, or built locally by the launcher on first use.

## Delivery order

1. Format v2 read alongside v1, and the conversion command.
2. Declared services in local mode, with the per-checkout lifecycle.
3. Declared services in the isolated environment, with the policy checks.
4. Toolchain image for the workspace container, gateway kept on the official image.
5. `environment verify`, its CI use, and the starter descriptions.
6. Enablement and use modes in `archetipo-environment` and in the viewer.
7. `coaching-planner` enabled as the first real project.
