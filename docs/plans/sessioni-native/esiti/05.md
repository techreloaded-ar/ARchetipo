Codex implementa ora `execution.SessionProvider` e View usa il percorso nativo

## Risultato e contratti modificati

- Aggiunto `cli/internal/execution/codex/native_session.go`:
  - crea `thread/start` con `ephemeral:false` e conserva `thread.id` come
    `codex.thread`;
  - riapre esclusivamente con `thread/resume` e verifica che l'ID restituito sia
    quello persistito;
  - mantiene una connection app-server tra più `turn/start`, usa `turn/steer`
    soltanto per il turn attivo e lascia il thread resumable dopo interrupt;
  - applica `model` ed `effort` a ogni `turn/start`, registra Requested/Applied
    dopo l'accettazione del runtime e non modifica il default del workspace;
  - scopre model ed effort con `model/list` e skill con `skills/list`, valida le
    skill selezionate e invia sia il marker `$name` sia l'input `skill` nativo;
  - esegue nel cwd della conversation senza richiedere spec o execution.
- Esteso il client app-server esistente senza creare un secondo protocol stack:
  handshake separabile, `thread/resume`, turn multipli, correlazioni
  turn/submission, stato terminale autorevole e server request instradabili.
- Le server request `item/commandExecution/requestApproval`,
  `item/fileChange/requestApproval` e `item/tool/requestUserInput` diventano
  rispettivamente `PendingApproval` e `PendingInput`; le risposte JSON-RPC
  tornano sullo stesso request ID. Le richieste non supportate ricevono un errore
  esplicito e non restano sospese.
- Aggiunta la rotta comune
  `POST /api/workspace/conversations/{id}/inputs/{inputId}` con persistenza della
  delivery prima e dopo il confine di trasporto, analoga alla rotta approval.
- `turn/completed` non equivale più automaticamente a successo: status ed error
  del turn determinano `COMPLETED`, `INTERRUPTED` o `FAILED`; la morte del
  processo senza `turn/completed` produce `FAILED`.
- Aggiornati `fake-codex.mjs` e lo smoke conversation esistente: Codex usa lo
  stesso contratto HTTP di Claude, senza UI o rail dedicate.

La skill `ponytail` ha orientato il lavoro al riuso di `appServer`, del journal
e delle rotte native esistenti, senza nuove dependency o framework. La
documentazione ufficiale OpenAI App Server è stata confrontata con il protocollo
effettivamente accettato da Codex CLI 0.146.0.

## Regole precedenti eliminate e decisioni

- Eliminato `ephemeral:true` dal percorso delle conversation durevoli; rimane
  soltanto nel percorso batch single-turn, che non promette resume.
- Eliminati il decline indiscriminato delle server request e i cataloghi statici
  come fonte delle capability native. Il catalogo statico resta soltanto come
  fallback configurabile del provider batch quando il runtime non è installato.
- La fine di un turn non chiude più l'app-server della conversation. Release,
  interrupt, fine turn e resume restano lifecycle distinti.
- Il resume non reinvia timeline o summary e non crea conversation ID, thread ID
  o rail entry nuovi.
- Il percorso native usa la policy interattiva `untrusted` con il sandbox
  configurato; i pulsanti comuni `allow`/`deny` sono tradotti nelle decisioni
  Codex `accept`/`decline`.
- Gli effort accettati dalla configurazione comprendono anche `xhigh`, `max` e
  `ultra`, già esposti dai runtime recenti; la discovery per conversation resta
  comunque autorevole.

## Limiti e handoff

- Il primo rilascio riprende il thread dopo restart/release di View; non mantiene
  vivo un turn durante lo shutdown dell'host. Questo resta scope del task 09.
- Il bridge espone le approval command/file e `requestUserInput` provate sul
  binary supportato. Le server request app-server ulteriori restano rifiutate in
  modo esplicito finché un task ne definisce semantica e UI.
- Il percorso batch conserva il proprio lifecycle single-turn ed ephemeral:
  non deve essere usato come implementazione delle conversation.
- Task 06 può usare `session.pending_inputs`, la nuova rotta input e le rotte
  native già comuni, senza introdurre controlli Codex-specifici.
- Task 08 può collegare una execution allo stesso `SessionTurn.ExecutionID`;
  non deve aprire un secondo app-server o un nuovo thread.
